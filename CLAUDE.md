# Walletly — инструкция для работы над проектом

## Формат работы

Это одновременно разработка проекта и обучение. Цель — не только получить работающий код,
но и чтобы я понимала каждое решение и могла повторить его сама.

### Текущий режим (с 2026-11-08): сначала сборка, разбор потом

Claude собирает этапы 1–2 целиком (весь backend + рабочий фронт), по одному коммиту на блок
в ветке `mvp`, без пауз на вопросы. Спорные решения — в `docs/` с пометкой «разобрать».
После сборки я смотрю и тыкаю проект, затем разбираем его по истории коммитов:
один коммит — одно занятие по циклу ниже. Блоки, которые ещё не разобраны, в «Текущем статусе».

### Цикл одного блока

1. **Claude делает блок** — небольшой законченный кусок: модель, эндпоинт, сервис, тесты к нему.
   Блоки маленькие: такие, чтобы их можно было разобрать за один раз.
2. **Claude объясняет**, что сделано и для чего:
   - какую задачу решает блок и как он связан с остальным проектом;
   - ключевые решения и почему выбраны именно они (какие были альтернативы);
   - на что обратить внимание: подводные камни, безопасность, типичные ошибки.
3. **Claude задаёт уточняющие вопросы на проверку понимания** (2–4 вопроса по блоку):
   - вопросы на «почему» и «что будет, если», а не на пересказ кода;
   - после моих ответов — **честная проверка**: что верно, что неверно или неполно, и правильный ответ.
     Не засчитывать частично верный ответ как верный, не смягчать ошибки.
     Если я ошиблась — объяснить, в чём именно, и при необходимости задать дополнительный вопрос.
4. **Обсуждение и решение дальнейшего шага.** По ходу я продумываю архитектуру или задаю
   уточняющие вопросы — вместе решаем, как поступить дальше. Claude не начинает следующий блок,
   пока текущий не разобран и не согласован следующий шаг.

### Правила

- Архитектурные решения принимаем вместе. Если есть варианты — Claude предлагает их с плюсами
  и минусами и рекомендацию, но выбор за мной.
- Принятые решения фиксируются в `docs/` (таблица «Принятые решения»).
- Комментарии в коде — на русском, объясняют «почему», а не «что».
- Каждый блок сопровождается тестами.
- Коммит — после того, как блок разобран и тесты проходят. Сообщения коммитов — на русском.

## Проект

Walletly — учёт личных и семейных финансов.

### Структура

```
backend/            FastAPI + async SQLAlchemy + PostgreSQL, менеджер пакетов uv
  app/core/         настройки (.env), подключение к БД, безопасность (пароли, JWT)
  app/models/       модели SQLAlchemy
  app/schemas/      Pydantic-схемы запросов и ответов
  app/services/     бизнес-логика (не знает про HTTP)
  app/api/routers/  эндпоинты: переводят ошибки сервисов в HTTP-ответы
  app/api/deps.py   зависимости FastAPI (сессия БД, текущий пользователь)
  migrations/       Alembic
  tests/            pytest, отдельная тестовая БД walletly_test
docs/               решения по архитектуре: db-schema.md, auth.md, api.md
frontend/           рабочий интерфейс: Vite + React + TanStack Query, nginx в Docker
frontent/           старый прототип (vinext) — отдельный git-репозиторий,
                    карта экранов в frontent/PRODUCT_PAGES.md
docker-compose.yml  PostgreSQL 17
```

### Команды

```bash
docker compose up -d --build                # всё приложение: http://localhost:8080
docker exec walletly-api python -m app.seed # демо-данные, логины напечатает команда
docker compose up -d db                     # только БД, для разработки
cd backend
uv run uvicorn app.main:app --reload        # запустить API без Docker
uv run pytest                               # тесты
uv run alembic revision --autogenerate -m "..."   # новая миграция
uv run alembic upgrade head                 # применить миграции
uv run alembic check                        # модели совпадают с миграциями
uv run python -m app.cli make-admin <email> # выдать роль администратора
cd frontend
npm run dev                                 # фронт на Vite, API_URL — адрес бэкенда
```

Порты задаются в `.env`. На этом компьютере 5432 и 8000 заняты другим проектом,
поэтому Walletly использует `POSTGRES_PORT=5433` и `API_PORT=8001`.

### Ключевые решения (подробно — в docs/)

- Данные принадлежат пространствам (ledgers): личное у каждого пользователя, семья — общее.
- Остаток счёта не хранится, а вычисляется по транзакциям.
- Переводы — `type = transfer` + `to_account_id`, не искажают доходы/расходы.
- Авторизация: access JWT (15 мин) в заголовке + refresh (30 дней) в httpOnly cookie с ротацией.

## Текущий статус

Этапы 1–2 собраны в ветке `mvp` (backend, фронт, запуск в Docker). Решения сборки — в `docs/api.md`, все «разобрать».

Не разобраны со мной (идём по `git log` снизу вверх, один коммит — одно занятие):
1. Вход, обновление сессии, выход (вопросы уже заданы, ответов пока нет).
2. Текущий пользователь, профиль, пространства.
3. Счета с вычисляемым остатком, категории.
4. Операции, фильтры, аналитика.
5. Приглашения, админка.
6. Импорт Excel/CSV.
7. Фронтенд: клиент API, refresh между вкладками, экраны.
8. Docker: сборка, nginx, compose.

Дальше, после разбора: этап 3 (деплой, HTTPS, бэкапы), затем ML и оплата.
